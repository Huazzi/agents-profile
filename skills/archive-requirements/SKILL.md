# 需求实现归档

把散落的需求与开发过程材料整理为本地 Markdown：一个共享目录页，每个需求一份需求文档和一份技术方案。成稿记录指定阶段最终采用的行为，过滤草稿、会议、中间决策和操作回执。正文不写来源章节、核对分支提交清单或本机路径。

## 1. 确定范围与基线

- 读取项目规则及已有目录、成稿。确认需求材料位置、输出位置、需求编号和本次新增/更新范围；已有授权和上下文中的确认持续有效。
- 确认每项需求当前进度：测试中、灰度测试中或已上线。通常按上线后的实现归档，但允许用户指定其他阶段；无法确定且影响结论时，直接询问用户，不从目录名或文件时间推断。
- 确认该阶段对应的源码分支，以及必要的需求开发分支。优先使用项目明确的环境映射；分支含义或交付关系不清且影响最终规则时询问用户，不默认主分支就是线上分支。
- 记录初始工作区状态。优先通过 Git 只读命令比较引用，避免为阅读切换分支或改动工作区。
- 核对本地/远端引用的新鲜度，按需要刷新或查询远端。远端不可用时说明实际读取的本地基线；可以继续准备文稿，但不能宣称已验证远端最新实现。

完成条件：每项需求有明确的目标阶段及可读取基线；关键歧义已解决或明确列为待确认，不凭猜测定稿。

## 2. 核对最终规则

先盘点、再读原始需求和可能的定稿，随后阅读目标基线中的实际调用链。文档标题“最终版”、最高版本号、最近修改时间和历史开发总结都只能作为线索。

围绕每个核心规则，核对入口、状态转换、DAO/SQL、下游调用、回调推进及相关持久测试中实际涉及的环节。测试用于理解和交叉检查契约，不能替代生产实现；单纯文档归档通常无需启动应用或运行会访问真实资源的测试。

存在需求开发分支时：

1. 核对与目标分支的祖先关系、合并情况及相关文件差异。
2. 从需求分支识别本需求意图，沿目标分支核对后续修复、回退和生命周期变化。
3. 按用户指定阶段的实际实现写成稿。开发分支独有的未交付行为不得写成线上能力；两边冲突且无法确定取舍时，询问用户。

重点区分：

- 新请求与已排队、已准入、执行中和已终态实例。
- 关闭、逻辑删除、物理清理及恢复。
- 候选查询与最终匹配，配置默认值与环境实际值。
- 主路径与兼容、重试、异常路径；“优先按旧版本”不等于“绝不回退”。
- 本地事务与跨数据库/服务/消息系统的真实边界。

在工作笔记或任务上下文保存“规则—代码依据—冲突处置”，不将其复制为成稿的来源列表。关键规则发现冲突时，追踪到实际分支、条件与调用，更新所有受影响表格、场景及图示，而非仅修正一句话。

实现不能说明的意图，不编造为“最终决策”；旧材料中的愿望也不补成现有能力。关键实现或上线范围仍不明确时，仅就缺失点向用户确认，继续处理其余确定内容。

完成条件：每个核心规则均有当前实现或明确产品确认支撑；关键反例已检查，旧文档与实现的冲突有明确处置。

## 3. 编写两份成稿

阅读 [成稿模板与风格](references/templates.md)，按需求性质裁剪。功能需求侧重操作与规则，Bug 侧重现象、修复后的行为及边界。模板是结构参考，不是必须填满的章节表。

默认输出结构：

```text
整理成稿/
├── 目录.md
├── 需求文档/
│   └── R00X-提炼的需求名称.md
└── 技术方案/
    └── R00X-提炼的需求名称.md
```

沿用项目已认可的输出位置和编号；两个子目录中的同一需求使用相同编号与提炼名称，以目录区分文档类型。编号超过三位或项目使用其他前缀时沿用项目惯例。修订既有成稿时原位更新，避免增加“新版/最终版/最终最终版”副本。

- 需求文档让产品与业务读者理解背景、目标、最终业务规则、场景及业务边界，减少实现类名和内部状态码。
- 技术方案让研发理解实现机制、数据流转、状态与持久化、异常、一致性及必要技术边界，按需引用类/方法名，不列本机文件链接。
- 采用当前实现的陈述语气。历史过程只在解释现有机制确有必要时压缩为原因，不保留讨论、备选方案、评审过程或部署回执。
- 适合时使用 Mermaid 数据流、时序或状态图；图示表达实际条件和阶段，不把“新实例启动准入”画成每个后续节点都重新准入，也不把逻辑删除画成运行实例自动终止。
- 保留真正影响理解的限制，不新增推测功能、无关技术细节或假想风险清单。按需使用表格和具体场景。
- 原始材料保留。截图只在确有解释价值时使用；准备导入时确认图片路径与平台承载方式。

完成条件：每项两份可独立阅读、彼此规则一致的文稿，阶段准确，内容没有来源章节和中间过程记录。

## 4. 同步维护共享目录

每次新增、改名、移动或删除成稿，都在同一轮更新目录页：

- 每个需求恰好一个导航条目，包含编号、名称及两份成稿的有效链接。
- 新增需求补入原共享目录，保留原有条目和排序惯例，不为每次追加任务另起孤立目录页。
- 改名或移动同步修复旧链接；原位内容修订而路径未变时无需无意义重写条目。
- 在有助阅读时简述需求之间的关系，避免在目录重复维护详细业务规则。

完成条件：本次及已有需求都能从共享目录到达两份文稿，没有漏项、重复项或断链。完整归档 N 项时，应为一个目录页加 2N 份成稿。

## 5. 交付前检查

逐项复核：

1. 两份文稿与目标基线一致，已覆盖本需求后续修复及兼容例外；表格、场景、文字与图示表达相同规则。
2. 成稿不混入草稿决策、现场数据、敏感信息、来源章节或本机路径；未将未核实能力写成承诺。
3. 名称、编号、标题、类型和阶段一致；目录覆盖完整，链接有效；Markdown 围栏及 Mermaid 结构正确。未实际渲染时不要声称图已完成渲染验证。
4. 修改限于任务相关文档，原材料和用户已有修改保留；按仓库要求检查差异。文件被 Git 忽略时检查实际文件，不用空 `git diff` 证明内容通过。

交付时给出目录页或本次更新文档链接、数量和重要修正，以及仍影响准确性的基线/范围限制。静态核对、测试执行、部署和业务验收分别陈述。

默认交付本地 Markdown。用户确认内容后再按明确请求使用平台工具或人工导入；创建成稿本身不授权上传、发布、提交或推送。
