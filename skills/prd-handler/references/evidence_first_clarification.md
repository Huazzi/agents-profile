# 证据优先的需求澄清

评估、生成问题、更新工作稿时使用本 reference。先按 SKILL.md 的分析流程形成内部工作底稿；仅启用代码事实辅助模式时执行定向代码探索。归档阶段不加载需求内容或执行本流程。

## 1. 候选问题分类与处置

| 类型 | 判断依据 | 发问前动作 | 对外处置 |
|---|---|---|---|
| 代码事实问题 | 询问当前系统实际做什么、是否支持某边界 | 先定向核查，记录 CF 编号 | 事实清楚则已查证关闭；关键证据不可取得时请求补证 |
| 业务决策问题 | 目标、范围、规则或取舍需要负责人决定 | 引用明确需求及已知前提，不做无关代码探索 | 待人工决策，提出具体选择 |
| 事实与决策混合问题 | 把现状与“本期要不要做”混在一起 | 拆成关联事实项和决策项，先查事实 | 仅询问剩余差异，事实部分不重复询问 |
| 需求与现有实现冲突问题 | 材料目标和已查证行为不同 | 并列保留目标来源、现状证据和差异 | 目标含糊或材料互相矛盾时询问沿用/改变；目标明确要求改变时转为明确变更需求，只问尚未明确的边界 |
| 证据不足问题 | 核查受限、缺少部署配置/上下游/运行证据等 | 记录原问题性质、已查范围、已得证据及缺口 | 可继续定向核查则内部处理；不可取得且影响判断则向责任方补证，不能改写成“是否实现”的产品选择 |

混合问题示例：“撤回功能本期要不要实现？”拆成：

- 事实项：核查申请人是否能在待审批状态从指定入口撤回本人数据，是否完成状态写入、通知及异常处理。
- 决策项：材料是否要扩大到审批完成后、其他角色或批量入口；已有明确目标时直接记录为需求，不再请用户重复批准。
- 事实项即使已查证关闭，决策项仍独立存在。若当前覆盖已与明确需求完全相符，只需补齐有需求依据的验收与回归说明；不得据此把代码里的其他行为一并纳入需求。

无代码库时仍分类和登记问题；代码事实项写明未核查原因，必要时请求现状材料或责任方说明，不伪造 CF 结论。纯业务选择可以正常提交。

## 2. 定向代码探索与停止条件

1. **限定命题**：为每条待核查事实绑定需求/Q 编号，写出要验证的行为、覆盖维度、相关模块及预期证据；先查看适用的仓库指导。用路径、业务术语和已知入口定向搜索，命中名称只作为线索。
2. **锁定基线**：记录仓库绝对路径、分支及 commit（能取得时两者都记）。记录未提交改动对命题的影响，必要时附相关文件内容摘要或哈希；无 Git 元数据时写“版本无法确认”并记录快照标识/核查时间及限制。仓库代码不能直接证明线上已部署或开关已启用。
3. **追踪行为**：从入口/调用方到核心逻辑、状态与权限判断、数据读取和写入，检查涉及的接口、事件、消息生产与消费、配置与功能开关、相关测试，以及需求对应的错误、重复、越权、跨数据范围等边界。沿调用顺序跟踪参数转换、条件和提前返回，确认检查在真实路径中对什么值生效；辅助函数中的检查不能单独证明整个入口具备相同保证。每个与命题相关的环节给出证据；不适用项说明原因，缺失项写未知，不能为了填满清单扩展到无关模块。
4. **核对覆盖**：按“目标—实际行为—角色—状态—入口—数据范围—异常边界”逐项比较。测试文件或字段存在本身不是通过证据；区分“读到测试断言”“已有运行结果”“部署运行事实”。本阶段只读审阅代码、测试与配置，不修改仓库或通过迁移、配置变更来验证猜想。
5. **收束**：证据足以判定该命题及相关边界时停止；发现仍需业务选择时记录后提交决定；访问受限、跨仓库/部署证据缺失或下一步已超出相关业务链路时，记录限制与补证方向后停止。新增范围须由具体缺口驱动，而非默认全仓扫描。

采用以下结论，结论始终只针对记录中的命题和版本：

| 结论 | 使用条件 |
|---|---|
| 已实现 | 相关真实链路及所需覆盖维度有充分证据；将未验证的部署/运行条件明确列为限制 |
| 部分实现 | 已证实可工作的子集，同时已知其余目标未覆盖或链路缺段；逐项列出覆盖和差异 |
| 在核查范围内未发现 | 在明确模块、入口和搜索范围内未找到支持证据；不能写成“系统不存在该能力” |
| 无法确认 | 仅有接口/类名/数据结构等线索，或关键链路、版本、权限、配置等证据不足以判断 |

“只有接口”的情况：存在已验证子集时为部分实现；只有声明而无法确认可工作的行为时为无法确认。代码与测试、不同版本或运行材料冲突时保留双方证据，降低结论确定性并转待补充证据。

## 3. 统一代码事实记录

每个命题一条记录。下面的字段是事实记录的唯一格式；评估、问题包或工作稿用 CF 编号引用，只有本轮新增/修订记录需要展开，未变化的记录引用不可变历史工件及章节，避免指向会覆盖的“最新”文件。

```markdown
### CF-001：<核查命题短名>

- 关联需求/问题编号：<REQ/BR/AC/Q 编号；混合问题关联事实与决策子项>
- 核查命题：<可证实或证伪的具体行为和预期覆盖>
- 仓库路径：<绝对路径；多仓库分别列出>
- 分支 / commit：<分支和提交；无法取得则写明>
- 核查时间与工作树：<时间；相关未提交差异/文件哈希/快照标识及影响>
- 核查范围：<模块、入口、链路、搜索范围；不包含什么>
- 结论：<已实现 / 部分实现 / 在核查范围内未发现 / 无法确认>
- 实际行为：<逐项描述可观察到的代码行为，与推断分开>
- 覆盖边界：<角色、状态、入口、数据范围、异常边界；未知或不适用需说明>
- 关键证据：<仓库内路径:行号 + 符号 + 调用路径；绑定上述版本>
- 测试 / 配置 / 接口证据：<路径:行号、断言或契约、开关默认值；只读/运行结果来源/未验证>
- 与需求的差异：<新增能力 / 扩大覆盖 / 修改行为 / 仅补验收回归 / 待确认；逐项关联需求来源>
- 未知与限制：<未核查部分、缺失证据、代码与部署差异；不确定性影响什么>
- 后续补证：<已查范围与已得证据摘要；还缺什么；建议检查方向；责任方；无则写无>
- 问题处置：<关闭哪个事实项、保留/重写哪个决策项、补证请求及是否阻塞和依据>
```

代码事实与已确认产品需求分别存放。产品确认引用原始需求或实际人工答复；事实记录引用源代码。即使用户选择沿用现状，也要记录选择覆盖的具体规则和 CF 版本，不能用“全部按代码”隐式批准未列出的行为。

## 4. 候选问题台账与状态

台账覆盖所有候选项，而非只有本轮对外问题。兼容现有 Q-B/Q-N 编号；沿用编号，阻塞级别单独维护，变化时不重新编号。拆分项可使用 `Q-B-001-F` / `Q-B-001-D`，保留原项及关联关系，不能丢失原问题。

| 状态 | 含义与退出依据 |
|---|---|
| 待核查 | 需要内部事实核查，尚未得出可靠结论；查明后关闭或进入补证/决策 |
| 待补充证据 | 已记录核查限制与缺口；取得证据后回到核查或形成结论 |
| 待人工决策 | 负责人需要做具体范围、规则或协作选择；明确答复后才可确认关闭 |
| 已查证关闭 | 代码事实命题已明确，且证据足以回答该命题；不表示本期业务范围获批 |
| 已确认关闭 | 原始需求已明确回答或人工已明确确认，记录来源、确认范围与方式 |
| 已合并 | 重复项或已拆分父项保留索引，指向承接编号；不意味着承接项已解决 |

台账每项至少包含：问题编号、关联需求、候选原问、类型（证据不足项保留原性质）、事实/决策拆分关系、核查命题/CF 引用、当前状态、阻塞级别及依据、确认/补证对象、处置说明、合并去向、状态变更记录（原状态→新状态、原因、证据/答复来源、日期）。无相关代码事实时明确不适用。

已关闭项默认延续关闭，不进入后续轮次对外清单。只有需求变化、相关代码版本变化、证据失效或冲突时才重开；记录触发原因、失效的记录、影响范围和新状态。新 commit 不必令所有事实失效，只重查受影响命题；影响无法判断时标记待核查。待核查/补证/决策项只要影响范围、验收、风险、权限、数据或技术方案，就必须记录具体影响并作为阻塞；其他遗留项说明为何非阻塞。

已合并项的阻塞状态由承接项决定；定版前沿关联关系检查，不能靠合并/拆分清空阻塞。事实命题已经回答但发现另一个能力缺口时，新建/保留差异决策项，不把“已查证关闭”当成需求完成。

## 5. 记录落点与轮次承接

- **内部工作底稿**：先从来源形成结构化需求清单，再识别疑点。每项含需求编号、原文/来源、目标行为、来源状态及待补内容。已有工作稿时形成相对其版本的增量，没有时形成初始快照。该准备本身不调用 `publish-draft`。
- **本轮发布**：评估或问题包模板的内部分析记录中保存工作底稿增量、完整候选台账，以及本轮新增/修订 CF；工作稿更新阶段将其统一纳入工作稿。内部台账与对外问题清单分别统计；无可对外问题时清单为空，报告核查结果或剩余补证任务。
- **承接**：标注本次记录依据的工作稿、评估、问题包、澄清结论的具体历史路径及版本，记录台账承接自哪一份。下一轮读取这些工件并追随明确承接关系；不同工件的 RNN 是独立序号，不能比较大小来判定谁更新。冲突时回查历史和来源，先解决冲突再生成问题。
- **落盘边界**：所有记录位于现有四类工作区工件中，随当前阶段的原命令版本化发布，不新增目录、状态数据库或发布命令。仅记录反馈时在澄清结论内保存所答问题的状态变化，下轮分析再并入完整台账。

## 6. 对外问题与补证请求

对外问题询问“现状与目标之间的差异如何处理”。阻塞与非阻塞问题均写明：已知现状（区分材料明确、人工确认和代码观察）、证据引用、材料中的缺口、具体人工决定、可选方案、推荐及依据、对范围/验收/数据/权限/兼容性/风险的影响，以及是否阻塞需求定版或后续技术工作。不涉及代码时填“不适用”，不编造证据。影响不涉及的维度也可明确写不涉及。

无法确认现状时不要伪装成“已确认现状”；列出已知部分与未知。补证请求单列，写责任方、缺失证据、已查范围、下一步方向与阻塞依据。若需要协作决定，询问“由谁提供哪项证据/是否接受明确的核查限制”，不能用产品选项让真人猜系统行为；接受限制也不等于该事实为真。推荐不构成确认，证据未知也不能变成默认实现或范围决定。
